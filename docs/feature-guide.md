# Sharktooth feature guide

Detailed operation and compatibility notes for the features in the [README](../README.md); see [diagnostics](diagnostics.md) for troubleshooting.

## Features

The app opens on Dashboard. Use the right-hand sidebar to switch pages; its blue selection highlight slides to the tapped tile with an ease-in/ease-out animation. A compact sidebar, header, and outer margins leave more room for content. Cards and sections are borderless in both styles, and floating panel shadows extend into the outer app margins. Settings and Debug remain in the top row with full-size touch targets. Leaving Pet Mode from the sidebar restores its previous climate and brightness settings.

Classic uses the same cabin-photo background at the same opacity in light and dark mode, visible through the translucent page and sidebar. Modern keeps its solid background. Default labels, controls and input text follow the selected text palette across all pages: dark grey in light mode and light text in dark mode. Camp Mode places both cards directly below the tabs and displays Actions in two columns, with scrolling available when needed.

**Controls Bar** — This sidebar item appears when the DiKey buttons are connected; debug builds always show it for testing. Select it, then use the **Colours** and **Buttons** tabs to switch between lighting and button mapping.

**Colours** — Set ambient bars (left, middle, right) and DiKey backlight. Tap a collapsed summary to expand that zone; the other zones collapse. Matching values line up across the cards. Use the colour bar, saturation, brightness and RGB sliders to adjust the active zone; the marker above the bar shows the selected colour. The page opens on the day or night profile currently shown on the bar, so changes are applied and saved to the colours that remain after leaving. Selecting the other profile previews it on a connected DiKey, with colour updates sent throughout a slider drag rather than only when it stops. Automatic ambient-light switching is paused while this page is open and resumes when you leave. **Sync bar colours** combines the three bar controls, leaving key backlight and each bar's mode independent. The first time sync is enabled, each day/night profile uses its left bar's colour. Turning sync off restores the separate colours; turning it back on restores the last synced colour for each profile. The image above the controls previews the bar and key backlight colours as you edit the day or night profile, with glow reflecting their brightness; it does not animate lighting modes. Its dials show the latest known values on the connected DiKey, and are blank when the display is off or its value is unknown. Debug builds show labelled example dial values while disconnected. Pick modes (solid / breath / blink / flow / off) when sync is off. Day and night profiles switch automatically from the vehicle ambient-light sensor (same signal as auto headlights / tunnels).

**Button mapping** — Down click keeps climate (as printed) unless remapped. Down long, up, and up long can open apps or run Android Intents (activity / broadcast).

The Colours page uses darker segment panels in light mode and a filled **Sync bar colours** button. Bar modes are selected directly from the slim horizontal **Off / Solid / Breath / Blink / Flow** button row beside the **Mode** label; the selected mode is highlighted. Light-mode button labels use dark text. Temperature dial previews use a third seven-segment position with only its upper loop lit as a degree symbol; fan and volume values have no degree symbol, and single-digit values have no leading zero.

**Dials** — Left dial = passenger, right dial = driver. Click to switch between **temp** and **fan**, rotate to adjust. Each dial returns to temperature after 3 seconds without a turn in fan mode.

**Dashboard** — Live cards for battery, range, fuel, driving data, tyre pressures, vehicle attitude, and head-unit resource usage. Cards fill three columns from left to right, then continue on the next row, with the whole dashboard scrolling together. All nine existing cards appear initially. Hold any dashboard card for **1 second** to enter edit mode; normal taps and scrolling do not activate it. Holding the Dashboard sidebar button for **1 second** also works, including from another page. Each card has a small, round red remove button overlaid in its top-right corner, with a larger invisible touch target; editing does not move the card contents. Hold a card and drag it to reorder. A blue insertion marker shows where it will go: the left/right half of a card selects before/after that card, gaps between cards work too, and the next free slot moves it to the end. When the marker stays in one position for **half a second**, cards animate aside to leave a blank drop slot, including wrapping onto the next row. This previews the resulting layout without saving it; moving to another insertion point restarts the delay, and leaving the dashboard or cancelling the drag restores the cards. Releasing saves the insertion order, rather than swapping; drag near the top or bottom edge to scroll. The large **+** in the next free slot opens a scrollable library of visual card previews, including their titles and live contents, on a contrasting slate background that follows light/dark mode. Tap a preview to add that card. Only cards not already on the dashboard can be added; removed cards return to the library. Changes save automatically and survive app restarts, including an empty dashboard. Tap **Done** or Back to leave edit mode. Outside edit mode there is no page heading, leaving more vertical space for the cards.

Swipe left or right, or tap one of the five dots at the top, to switch dashboards. The cards follow your finger as you drag. When you release after a swipe, the current cards finish sliding out while the next cards finish sliding in. A short drag slides back to the current dashboard. The largest dot marks the current dashboard. Page one keeps your existing layout; pages two through five start blank. Tap **Edit this dashboard** on an empty page to add cards. Each page saves its own card selection and order, and you can use the same card on multiple pages. Tap **Done** before switching pages.

Dashboard cards show their key readings in large type at the top right: battery health, speed, tyre status, lifetime fuel economy, EV and HEV distances, pitch and roll, CPU usage, engine RPM, and outside temperature. The Engine card plots RPM over a rolling hour using readings collected while Dashboard is open; gaps indicate periods without readings, and history resets when the app process restarts. The Drive card’s gauge extends up into the space beside the gear readout and scales down to keep the card within half the visible Dashboard height. The accelerator uses a blue outer arc and the brake a yellow inner arc (`#FFCC00`). The centre shows the active pedal and its percentage in bold white, with Brake taking priority if both report activity. The gear readout is larger than the Park brake status, with the gear value in bold. Park brake status sits at the bottom left. Tyres shows **OK** only when all four report normal status. The charge bar is blue (`#0090FF`), and the fuel bar is light green (`#00FF5D`). Only the filled portion of each bar glows.

Small captions beneath the top-right values identify each reading. The Mileage card uses muted EV and HEV labels so the distances stand out, and places the odometer, drive time, and average speed at the bottom. The Drive gauge keeps the same vertical position when the speed or gear text changes. Pitch / Roll shows angles on its two instruments rather than repeating them in the header. The EVAKOOL card centers its logo and readings, with large left and right temperatures side by side.

Debug builds label the Dashboard **Sample data** and show example readings on every card, including the optional fridge card. Saved card layouts are unchanged. The sample fridge card is display-only, and release builds continue to show live data.

The **Pitch / roll** card always shows two circular blue-accented instruments: **Pitch** on the left with the side Shark photo, and **Roll** on the right with the front profile. The gauges map the head unit's accelerometer axes to the vehicle's pitch and roll. Smooth translucent faces without background grids follow light/dark mode, with larger bold upper scale labels and longer, heavier major ticks for readability. Each vehicle and its thicker ground line rotate smoothly together inside a fixed graduated ring; the ground stays in contact with the tyres and is clipped to the dial. The live angle is raised a further 10% of the gauge height from its previous position. Missing readings display a dash rather than a false zero. The photos and pointer stop at ±45° to remain within the instruments, while the numeric readouts retain the actual measured angles. These replace the old artificial horizon and Split switch; the dashboard grid and editing controls are unchanged.

The Engine graph shows RPM ticks on the left and elapsed-time labels along the bottom, from **−60 min** to **Now**. The Drive gauge shows a small, raised percent sign beside the live pedal value. It marks each pedal’s highest reading with a dot and lists both peaks at the bottom right. Peaks are based on readings collected while Dashboard is open, survive app restarts, and reset for each local calendar day.

The optional **EVAKOOL fridge** card is always available in the dashboard library, even before a fridge connects; it is not added automatically. Left and right temperatures are side by side in the header, with battery voltage and Eco/Max side by side below. The card also shows power (On/Off) and how many seconds or minutes ago the last status was received. When disconnected, it shows **Fridge disconnected** and a Reconnect button. Tap the live card outside edit mode to open the full fridge controls and temperature history. The selected card remains on the dashboard across restarts, including while disconnected.

**ADAS** — View current driver-assistance settings or save and apply a custom ELKA, LDA, AEB, and DMS profile. Long-press the ADAS tile to configure automatic application when the app starts.

**Settings** — Updates appear first, above Appearance, Startup, Wi-Fi and Telemetry. Under **Appearance → Sidebar position**, choose **Left** or **Right**; Right is the default. The saved position applies to all sidebar pages when returning from Settings and survives app restarts, without mirroring the page contents. The compact **Sentry** section at the bottom replaces the old sidebar button and page. It retains install, reinstall and open controls for Overdrive and [Strike](https://github.com/DJS91/Strike), including package-change detection and installation progress. Each app's **Details** button shows its description and any setup notes.

**Modes** — The sidebar opens Camp Mode, with tabs for **Pet Mode** and **Camp Mode**. With the vehicle ON and safely parked, keep hands and objects clear of all windows before pressing **Enable Camping Mode**. The button starts preflight immediately without a confirmation popup. Camp Mode rechecks Park and battery charge in preflight and saves the original settings before applying **DiKey lights OFF (if connected) → disconnect active CarPlay → head-unit Bluetooth OFF → climate OFF → close all windows → DRLs OFF → dim instrument cluster → HUD OFF → mute media → screen OFF**, in that order. The instrument cluster is dimmed to its minimum nonzero brightness (`1`); HUD OFF is state `2`. Camp Mode never changes the headlights.

The **Actions** checklist has space below its last row inside the card, with more room between and below rows on taller screens. It marks a step only after success, with a half-second pause before the next step. Confirmed checks survive navigation and restart and reset after successful restoration. A failed step stops entry; **STOP WINDOWS** is available during entry and is pinned outside the scroll area. Park is checked immediately before every cluster or HUD write, during entry and restoration.

The **Disconnect Phone** action disconnects the active CarPlay session. Turning off head-unit Bluetooth remains a separate action.

**Save SoC** in the right card mirrors the vehicle's infotainment shortcut. Use the switch beside the heading to turn it on or off. When on, release the slider to apply the selected percentage. The range is 25–100%, capped at the firmware's advertised maximum when lower. The last reported target is shown even when Save SoC is off; the slider is disabled in that state. Sharktooth reads back each change and reports if the vehicle does not confirm it. This is separate from the Camp Mode battery cutoff and is not changed automatically when Camp Mode starts or ends.

Waking the screen ends Camp Mode and restores the original cluster and HUD settings first, then enables head-unit Bluetooth and connected DiKey lighting and restores media and DRLs. Windows stay closed and climate stays OFF. Remain in Park while settings restore. A wake during the screen-off command queues restoration until the command finishes. If restoration is incomplete, use **Retry restoring settings**; the app retains the originals until restoration succeeds. After successful restoration, a popup reminds you to turn the headlights back on and verify normal lighting before driving. Camp Mode does not keep the vehicle powered or monitor occupants.

**Camp Mode cards and battery cutoff** — The left card shows Camp status, gear, traction-battery charge and the Start control. Until Park is confirmed, the Start control is greyed out and reads **Waiting for vehicle Park Gear**. Once Park is confirmed, starting still requires a readable battery charge above the cutoff. The right card shows the saved cutoff (10% by default) and the read-only checklist instead of a debug report. Set the cutoff before starting; it cannot be changed during a session. Once Camp is active, Sharktooth checks the traction battery about every five seconds while its process is running, even if the Camp page is closed. A valid reading at or below the cutoff triggers the same restoration as waking the screen. Missing readings do not trigger restoration, and the cutoff cannot turn the vehicle off.

Camp Mode intentionally leaves climate **OFF** on exit, even if it was ON before camping or was switched ON manually during camping. It does not restart HVAC or reapply the saved temperature, fan, mode, recirculation or compressor profile. This also applies when retrying older saved sessions; Pet Mode restoration is unchanged. Entry and exit share the same OFF control: two consecutive OFF readings confirm success, an already-OFF system needs no command, and a delayed confirmed OFF supersedes an earlier command failure while retaining that diagnostic detail. Accepted-but-ignored commands and unreadable power remain explicit failures, so saved sessions remain retryable. Switch climate ON manually when needed.

The ten checklist actions fill three columns from top to bottom (four, three, then three). Labels wrap within their column; one-second gaps and the pinned **STOP WINDOWS** button are retained.

**Headlight-triggered start and exit are disabled.** A physical AUTO/OFF comparison on the connected head unit again produced invalid `0` from both selector getters and `-999999999` from the SDK auto-switch feature. Actual low-beam and sidelight feedback changed from ON (`1`) to OFF (`2`), but beams OFF cannot distinguish manual OFF from AUTO in daylight. Direct vendor-property access requires privileged OEM permissions; no bypass was attempted. Automatic entry and ON/AUTO exit must wait for reliable selector feedback rather than interpreting actual beam changes as stalk movements.

The separate diagnostic headlight controller still supports instrument `get(int[], Class)` feedback. It first requests the primitive integer format, then tries `BYDAutoEventValue` if the integer read is invalid, unavailable or rejected. Feature IDs come from the SDK's `BYDAutoFeatureIds.Instrument` fields when exported; otherwise the compatibility IDs are `1011875880` for feedback and `1276153912` for the selector command. These selector IDs are documented in [Overdrive's feature definitions](https://github.com/yash-srivastava/Overdrive-release/blob/main/app/src/main/java/com/overdrive/app/byd/BydFeatureIds.java). Read-only retries allow up to 1.5 seconds for a cold SDK connection; `0` and `-999999999` never count as OFF. An absent named setter can use the feature setter only with validated feedback; an existing named setter's rejection or exception never triggers a second, generic write. The interactive test report includes `Headlights.selector` and `Headlights.readPaths`. None of these diagnostic controls is used by Camp Mode.

The DiKey step affects the strip LEDs and key backlight, not the dial LCDs or ESP32 radio. If no DiKey is connected at entry, its lighting step is explicitly skipped. A temporary lighting override prevents ambient/profile updates and reconnect restores from relighting it while camping, without saving black over its colours; the override is recovered after an app restart. On exit, head-unit Bluetooth is always enabled, with adapter-state confirmation. Android 11 and older use the normal application's `BluetoothAdapter.enable()` / `disable()` APIs; newer Android versions retain the local-ADB `svc bluetooth` route. On this Android 11 head unit, `svc bluetooth disable` exited with code `137` without switching the adapter off. Separate normal-app API tests confirmed OFF and subsequent ON, each held for twelve seconds; original ON was restored. DiKey lighting is then re-enabled with its saved RGB/brightness values, even if its previous strip mode was OFF (changed to solid ON). Black/zero-brightness colour values remain unchanged. The ESP32's Bluetooth is never disabled. A native head-unit BLE DiKey connection can reconnect after Bluetooth is enabled; if the DiKey does not reconnect or its lighting writes fail, restoration remains retryable instead of reporting success.

The CarPlay step binds the installed OEM `com.ts.carplay/.CarPlayService` using its public AIDL interface and normal `CARPLAY_APP` / `CARPLAY_DEVICE_LIST` permissions. It reads the actual session state, disconnects only identified connected devices using `disconnectCarPlay(deviceId)`, and waits for inactive-state confirmation. On this firmware, both active wireless and connected-list CarPlay records can omit their device IDs. In that case the app obtains the actual ID from the OEM `IDeviceConnectionManager`, acquired through `ServiceProvider.get`, by uniquely matching the active device's Bluetooth address (or USB serial when no Bluetooth address exists). The address itself is never substituted for an ID; missing or ambiguous matches fail before any disconnect command. A readable CarPlay ID needs no extra lookup. An absent package or already-inactive session needs no command; unknown states and unconfirmed disconnection fail visibly. It neither forgets the phone nor disables Wi-Fi, and does not explicitly restart CarPlay on exit; reconnect normally afterwards. An isolated on-car test ran the compiled production controller through a normal-permission diagnostic context against an active wireless session: ID resolution succeeded and the session changed from ACTIVATED (`2`) to DEACTIVATED (`4`), confirmed independently by the OEM service. This did not activate Camp Mode or replace the installed Sharktooth app. Android's generic projection-service state is not authoritative for this OEM implementation.

CarPlay's API classloader uses only the Android framework as its parent, not Sharktooth's app classloader. The BYD vehicle SDK injects duplicate OEM provider classes into the app loader; inheriting them mixes those providers with the CarPlay APK's connection-manager interface and makes `ServiceProvider.get` return null (`OEM connection manager unavailable`). A read-only on-car comparison reproduced that failure after running Sharktooth's actual SDK injector, while isolating the installed CarPlay APK resolved the manager and its connected device. The separate CarPlay loader does not change the vehicle SDK's loading or request additional permissions. The targeted instrumentation test `activeCarPlayIdLookupSurvivesVehicleSdkInjectionWithoutDisconnecting` requires an active phone, resolves its ID after injection and verifies the session stays active without sending a disconnect command. A separate normal-permission diagnostic context ran both the old and fixed compiled production code after actual SDK injection: the old code reproduced the exact exception; the fixed code resolved one ID while leaving session `2` active, then a separate disconnect test confirmed session `2` to `4`. Bluetooth and Wi-Fi stayed ON. The earlier helper-only test had not injected the vehicle SDK and therefore missed this loader collision. These isolated tests did not activate all of Camp Mode or replace the installed app.

For BYD backlight-only sleep, Camp Mode also checks the captured centre-display `TsCarPower.setBackLightState` OFF-to-ON event through local ADB while waiting for wake. Only that log tag is read, and records before the screen-off action and other display types are ignored. Local ADB log access is checked before any settings change; if unavailable, entry fails visibly instead of relying on the wake tap reaching the app. The monitor stops when restoration starts.

**Camp Mode interactive tests** — Open Debug (bug icon) → **Camp Mode interactive tests** while safely parked. Capture a baseline, change one setting using the car's controls, select the matching label, optionally describe what you saw, and tap **Capture and compare**. Close the other windows before testing each window separately; capture Light, Dark and Auto display settings separately. Raw window identifiers and SDK constant values are included, but differences do not by themselves validate setter parameters. Captures and the baseline survive leaving the page or restarting the app. **Show results** stays in the page header and opens only the latest short result by default. **Raw details** is optional and opens the saved diagnostic history on screen; **Summary** returns to the short view. No export or sharing app is needed. Lighting inspections and headlight-OFF tests automatically display their latest results when the page is in the foreground. **Clear test session** deletes the local session without undoing vehicle settings. The confirmed **Test climate OFF** command requires confirmation, records the result and delayed power read-back, and leaves climate off (restore it manually). **Test display dimming** sets the centre display to 10% (never zero) with `BYDAutoSettingDevice.setInfotainmentBrightness` and Android's system brightness (Sharktooth grants itself **Modify system settings** over local ADB, because some head units have no screen for it). **Test screen off** sends the car's own Screen off shortcut command (starts `com.byd.carsettings/com.byd.dialogservice.DialogService` with `byd_pad://byd_car_settings:2935/launcher?action=screen_saver`, falling back to `am startservice` over local ADB); touch the screen to wake it. Dimming restores the previous brightness on touch, loss of foreground or after 10 seconds, and the report lists every command attempt. **Record car screen-off shortcut** reads the head unit's log over local ADB: start it, press the car's own Screen off shortcut, wake the screen and tap **Finish recording and show log**; the matching activity, broadcast, key and power/display log lines are shown on screen and added to the report. **Test close all windows** (car switched on) requires confirmation, sends the all-windows close command (`setAllWindowState(2,2,2,2)`, or `setWindowControlState([2,2,2,2])` on DiLink 5), and records each window's open percentage as it closes. **STOP WINDOWS** stays available during the test and halts all windows immediately. **Test daytime running lights OFF** (car in Park) requires confirmation, sends `BYDAutoLightDevice.setDayTimeLightState(2)` and confirms with the car's DRL read-back, because the car can accept the command without switching; **Restore daytime running lights ON** sends `setDayTimeLightState(1)`. Vehicle-theme command buttons remain locked pending verified mappings. These tests do not activate Camp Mode.

**Headlight / daylight debugging** — On the interactive tests page, **Inspect headlight and daylight APIs (read only)** records lighting-related method signatures, SDK/device constants, runtime classloaders and available scalar Light, Sensor, Instrument and other lighting getters. Raw `0` and unavailable sentinel readings are preserved, not reinterpreted as OFF. While parked, capture a baseline and compare separate physical-stalk OFF, AUTO, parking-light and low-beam positions using the matching labels. Ambient-light changes have a separate label. Inspection results appear automatically in an on-screen viewer. Headlight-OFF results put confirmation status, command details and the manual-restoration warning first. Use **Watch headlight stalk (live)** while safely parked, turn the physical stalk through OFF, AUTO and low beam, and pause two seconds at each position. The view samples lighting getters (including Bodywork rear-lamp feedback) and the head unit's local-ADB log about once a second, displays only changed readings and matching lighting events, and keeps just the latest eight events visible. The current rear-lamp raw value also stays in the header; it is not interpreted as the headlight selector or a verified headlight-control command. It does not send any vehicle commands or prove a logged event is a command that can be replayed. SDK-unavailable and ADB-denied states are shown explicitly; no events may mean the firmware does not expose them. **Stop capture**, closing the viewer or leaving the page stops sampling; the short final capture is saved for **Show results**. Full API inventories and raw snapshots are hidden behind **Raw details**, not displayed automatically.

The experimental **Test headlights OFF (named API)** and **Test headlights OFF (feature API)** buttons each require explicit confirmation, foreground and confirmed Park immediately before their single write. These manual tests may send OFF even when the previous selector is unreadable. The named test sends only `setHeadlightControlMode(1)`; the feature test sends only the SDK-resolved selector feature through `set(int[], BYDAutoEventValue)` with `intValue=1`. Neither automatically tries another API after failure, restores an unknown previous mode, or activates Camping Mode. SDK acceptance is reported separately from selector read-back and visual confirmation. Test one API at a time with the headlights visibly on, then **restore and visually verify normal lighting with the physical stalk before driving**. There is no automatic restoration. These controls remain separate from Camp Mode, which no longer sends headlight commands.

**On-car test: no lighting change (18 November 2026, BYD AUTO / Android 11)** — A separate, temporary diagnostic app sent **`BYDAutoLightDevice.setHeadlightControlMode(1)`**, not the Instrument device used by Sharktooth's current headlight tests. The app declared `BYDAUTO_LIGHT_COMMON`, `BYDAUTO_LIGHT_GET` and `BYDAUTO_LIGHT_SET`, and used granted gearbox-read permissions to confirm Park immediately before the single write. In a controlled repeat, the physical stalk remained untouched in AUTO and the visibly-on headlights **stayed ON throughout the 20-second observation**. The Light call returned **`1`**, while both devices' `getHeadlightControlMode()` readings remained `0` before and after. An earlier observation was confounded by manual stalk operation and is not evidence of success. This Light-device command did not switch the headlights off in the controlled test; its return value must not be interpreted as proof of a lighting change. Normal lighting was visually verified after testing. AUTO restoration and usable selector feedback remain unverified; no automatic Camp Mode integration was made. Sharktooth does not yet request `BYDAUTO_LIGHT_SET` or use this Light-device setter for headlights.

Further isolated tests used the OEM scene app's `BYDAutoBodyworkDevice.setModeCommand(int[16])` format, with only `COMMAND_OUTDOOR_LIGHT` (index `7`) populated: `1` from its camping scene, then `2` from its rest scene, in separate Park-guarded tests. Neither full scene nor its profile-setting command was invoked. Both calls returned `1`, but `Light.getLightStatus(LIGHT_LOW_BEAM=2)` remained `1`, sidelights remained `1`, and rear-lamp feedback remained `1` throughout ten seconds of sampling after each write. A subsequent physical-stalk comparison calibrated the beam feedback: user-confirmed headlights OFF produced low-beam and sidelight readings of `2`; returning the stalk to AUTO with user-confirmed headlights ON restored both readings to `1`. Thus these getters provide live on/off feedback on this firmware, whereas both headlight-selector getters remained invalid `0` in both physical positions. The HAL advertises the vendor selector and scene-vector properties, but does not advertise `OUTSIDE_LIGHT_STATE_SCENE_S` (`0x21403ee5`). The standard Android exterior-light permissions are `signature|privileged`; no permission bypass was attempted. None of these findings establishes a working software headlight-OFF control, and normal AUTO lighting was restored and verified after testing.

**On-car media mute: verified (18 November 2026, BYD AUTO / Android 11)** — Android reports `mUseFixedVolume=true`, but the OEM enhanced-audio service has separately mutable audio groups. The command `adb -s <head-unit-ip>:5555 shell input keyevent 164` (`KEYCODE_VOLUME_MUTE`) changed media group `0` from unmuted to muted, and the user confirmed playing media went silent. Media gain remained `3`; master mute and every other group's gain/mute state were unchanged, including call/safety group `5`. A second key restored media group `0` to unmuted with gain `3`, confirmed by read-back.

Read the OEM state with `adb -s <head-unit-ip>:5555 shell dumpsys car_service --services CarEnhancedAudioService`. Group `0` maps the MUSIC context to `bus0_media_out`; it is not Android's fixed `STREAM_MUSIC` volume. The key is a **toggle**, not an idempotent mute command: read the actual group state before sending it, verify the target mute state afterwards, and preserve the original for restoration. Do not substitute master mute or infer muting from successful key delivery.

Camp Mode now uses this path on fixed-volume head units instead of rejecting Android's fixed-volume flag. Preflight requires readable OEM group states and the verified single-zone, media-only group mapping and mute-key routing configuration. The app persists the original media gain, mute state and audio backend before any entry actions. It sends a key only when the actual media mute state differs from the target, polls for matching confirmation without ever blindly repeating the toggle, and checks that master mute, media gain and other audio groups remain unchanged. Originally-muted media stays muted on exit; restored sessions use their saved backend, while older sessions retain Android stream-volume restoration. Standard non-fixed Android audio behavior is unchanged.

Entry preserves media gain. On exit, the car path restores the saved gain even if someone adjusted it during camping, then restores the original mute state. The verified volume keys (`input keyevent 24` UP / `25` DOWN) adjust one step at a time, with actual group read-back after every key. On this head unit the first volume key while muted only unmutes without changing gain; confirmed unmuting permits the next adjustment key. Ignored keys, wrong-direction changes, failed reads/writes or changes to master/non-media audio stop restoration visibly and retain the saved session for retry. Originally-muted media is re-muted after gain adjustment if the volume keys unmute it. A host-side live test of the actual compiled backend restored saved gain `2` after an upward manual change to `3`, then restored saved gain `2` and original mute after a downward change to `1`. Final master mute and every audio group's gain/mute matched the original baseline exactly. These were isolated audio tests, not a full Camp Mode activation.

**On-car cluster dimming and HUD power: verified (18 November 2026, BYD AUTO / Android 11)** — The OEM infotainment controls delegate to `BYDAutoInstrumentDevice.setBacklightBrightness(int)` and `BYDAutoSettingDevice.setHudState(int)`. Separate, parked tests through the temporary diagnostic app confirmed:

- **Instrument cluster:** `getBacklightBrightness()` read `7`. Sending `setBacklightBrightness(1)` visibly dimmed the cluster, with read-back remaining `1` for six seconds. The exported brightness range is `1..22`; minimum `1` is dimming, not cluster OFF. Restoring the saved `7` was confirmed by read-back and visually.
- **HUD:** `getHudState()` read `1` (ON). Sending `setHudState(2)` visibly switched the windscreen projection OFF, with read-back remaining `2` for six seconds. Restoring the saved `1` switched it ON again, confirmed by read-back and visually. HUD brightness and height were not changed.

Both setters returned `0`, but success was established by matching read-back and independent visual observations, not the return code alone. The helper requests normal `BYDAUTO_INSTRUMENT_COMMON/GET/SET` and `BYDAUTO_SETTING_COMMON/GET/SET` permissions plus gearbox reads. It validates current values, persists each original before its write, and requires foreground and confirmed Park immediately before every change or restoration. Originals survive process restarts and are cleared only after matching restoration read-back.

Camp Mode now integrates these two verified controls using the app's existing normal Instrument/Setting permissions, with saved originals and matching read-back required for entry and restoration. This does **not** resolve the headlight-OFF issue: the tested head unit still returns an unreadable headlight selector. Camp Mode no longer blocks entry on that missing selector or an unconfirmed headlight-OFF attempt, allowing the other steps to run, but cannot restore an unknown original headlight setting. The isolated on-car display tests do not constitute a live test of the integrated Camp Mode sequence.

With the separate temporary `com.sphy.headlightprobe` app already installed, its DUMP-permission-protected ADB entry point is:

```text
adb -s <head-unit-ip>:5555 shell am start -S -W -n com.sphy.headlightprobe/.AdbProbeActivity --es mode <mode>
```

Use `displays-read` for a read-only baseline; `cluster-dim` / `cluster-restore` for minimum nonzero brightness / saved brightness; and `hud-off` / `hud-restore` for HUD OFF / saved HUD power. Wait at least 17 seconds after each changing command and inspect its report before continuing. Read the report with `adb -s <head-unit-ip>:5555 shell run-as com.sphy.headlightprobe cat files/headlight-probe.txt`. Test one control at a time, restore both and visually verify normal displays before driving. The helper is an external diagnostic app, not included in Sharktooth builds, and does not restore automatically.

No daylight-sensor spoof is implemented: infotainment Day/Night mode is not evidence that the exterior-light ambient sensor can be overridden. The inspection is intended to identify the car's actual lighting/sensor contract before any such control is considered; it never invokes discovered setters or guesses their arguments.

**Pet Mode** — Select the Pet Mode tab to keep the display awake and periodically enforce a configurable climate profile while the vehicle is **READY**. Fan speed, temperature, recirculation, and wind direction can be configured; the previous climate and brightness settings are restored on exit.

**Phone projection** — Open CarPlay or Android Auto from the shortcut at the bottom of the right-hand sidebar when a phone is projecting. In Settings, enable automatic switching to show a cancellable three-second countdown once a phone is connected and any enabled ADAS auto-apply has completed. Automatic switching works while the vehicle information screen is visible.

**ESP32 WiFi** — Connect the bridge to a [2.4 GHz network](esp32-wifi.md).

**Home Assistant telemetry** — Optionally send vehicle data via an ESP32 HTTPS webhook; see [telemetry setup and privacy](home-assistant-telemetry.md).

**Camping fridge (experimental)** — Monitor and control compatible [EVAKOOL fridges](camping-fridge.md).

**Background listener** — After you open Sharktooth, a foreground service keeps the USB/BLE DiKey link alive while the UI is in the background. Open the app once after power-on (see [autostart.md](../autostart.md) for DiLink limitations).

**In-app updates** — Home gear icon → **Check for updates** downloads the latest `open-dikey.apk` from [GitHub Releases](https://github.com/DJS91/Open-DiKey/releases).
